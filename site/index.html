      When a refusal looks like a success

      The database protected the row; the screen misread the answer. That is how row-level security is specified, not a Supabase defect. In this design a refusal is an explicit error, and the test fails when it is not.

      The audit log

      Only the database writes it, in the same transaction as the change. Signed-in users and the service key cannot add, edit or erase entries.

      What each entry keeps, and the limits

      For application changes: authenticated actor, checked workstation, before and after values, server time, and the measurement's operation key where applicable. Committed application changes to packs, measurements and holds record the requesting identity. A rolled-back change leaves no entry, and a refused call is not an audit event. The table owner can still remove entries, and there is no hash chain.

      First pass through your existing system

      Five steps, in this order. Scope and estimate are set after the inspection.

      1. Trace one pack

        Follow one serial through the browser, Windows workstation, functions and database, and map this flow's write paths and trust boundaries.

      2. Rank the blockers

        Give each blocker an estimate, an acceptance check and the remaining uncertainty.

      3. Fix the first blocker

        Show before and after on a representative Windows workstation, including interruption or restart, with a regression test.

      4. Rehearse deployment

        Check migration compatibility, distinguish app rollback from database recovery, and agree monitoring and failure ownership.

      5. Restore and hand over

        Restore the agreed scope, reconnect workstations, and document limits and remaining work.

      Claude Code reads the code and writes the tests. Permissions, transaction boundaries, recovery and what each test expects are checked against invariants written down separately.
