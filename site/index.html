      When a refusal looks like a success

      The database protected the row; the screen misread the answer. That is how row-level security is specified, not a Supabase defect. In this design a refusal is an explicit error, and the test fails when it is not.

      The audit log

      Written by a trigger inside the business transaction: actor from the signed token, workstation checked against the caller's stations, operation key, before and after values, server time. Insert, update, delete and truncate are refused to signed-in users and to service_role. A rolled-back change leaves no row, and a refused call is not an audit event. The table owner can still remove rows, and there is no hash chain.

      First pass through your existing system

      Five steps, in this order. Scope and estimate are set after the inspection.

      1. Reproduce one unit end to end

        Browser, workstation, server functions, database, on one serial.

        Proof a map of every write path and trust boundary.

      2. List the blockers

        What stops a release, ranked.

        Proof each blocker with an estimate, an acceptance check and the uncertainty left.

      3. Fix the first blocker

        One change, small enough to review.

        Proof before and after on a representative Windows workstation, in normal running and through a cut or a restart, plus the regression test that keeps it fixed.

      4. Rehearse a release

        On the deploy path you already have.

        Proof migration compatibility, app rollback kept separate from undoing a migration, monitoring, and who answers when it fails.

      5. Rehearse a restore and hand over

        For the scope agreed together.

        Proof the restore done, workstations reconnected, limits and remaining work written down.

      Claude Code reads the code and writes the tests. Permissions, transaction boundaries, recovery and what each test expects are checked against invariants written down separately.
